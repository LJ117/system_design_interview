# 设计聊天系统

## 12.1 理解问题并确定设计边界

1. 待设计的聊天应用种类
   1. 一对一单聊
   2. 群聊
   3. 大型群组互动和实时语音
2. 应用使用平台
   1. APP
   2. Web
3. 应用规模

## 12.2 提议高层级的设计

- 客户端和服务器通信的基本知识
  - 客户端
    - 可能是APP, Web
    - 客户端之间不直接通信
    - 每个客户端都连接到一个聊天服务
  - 聊天服务
    - 接受来自客户端信息
    - 为每条信息找到正确的接收者并发送
    - 接收者不在线, 服务器上保存消息, 直到上线再投递

1. 轮询
   1. 客户端周期性访问服务器是否有新消息
   2. 轮询频率和开销正相关
2. 长轮询
   1. 客户端保持连接处于打开状态
      1. 直到新消息可用 或者 连接超时
      2. 限制
         1. 发送者和接受这必须连到同一聊天服务器, 负载均衡可能导致失效
         2. 服务器无法判断客户端状态
         3. 效率不高. 如果一个用户并不经常聊天，长轮询依然会在超时之后周期性地建立连接。
3. WebSocket
   1. 服务器向客户端发送异步更新的最常用的解决方案
   2. 客户端发起, 双向且持续的
   3. 从 HTTP连接 升级到 WebSocket连接
   4. 服务端通过这个持久连接, 服务器向客户端发送更新信息

- 高层级设计
  - 无状态服务
    - 传统的面向大众的请求/响应服务，用于管理登录、注册、用户个人信息等
  - 有状态服务
    - 唯一的有状态服务是聊天服务
  - 第三方集成
    - 推送通知
  - 可扩展性
    - 聊天服务器实现消息的发送/接收。
    - 在线状态服务器管理在线/离线状态。
    - API服务器处理用户登录、注册、修改个人信息等任务。
    - 通知服务器发送推送通知。
    - 键值存储用于存储聊天历史。当离线的用户再次上线时，会看到自己之前的所有聊天记录。
  - 存储
    - 常规通用数据
      - 存关系型数据库
    - 聊条历史记录
      - 数据量庞大
      - 最近热点数据
      - 支持搜索历史记录
      - 使用 键值存储
        - 方便横向扩展
        - 访问延时低

## 12.3 设计继续深入

- 服务发现
  - 常见方案
    - Zookeeper, Nacos, Consul
- 消息流
  - 一对一聊天消息流
    - 明确发送和接收者
      - 针对接收者 是否在线 选择 推送消息/等待通知 处理
  - 在多个设备之间同步消息
    - 同一用户多个设备
    - 每个设备维护一个 cur_max_msg_id 用于追踪最新消息
    - 新消息判断规则
      - 接收者ID 是当前登录用户ID
      - 键值存储中的消息ID 大于 cur_max_msg_id
  - 群聊消息流
    - 每个接受者分配一个 接受消息队列
    - 限制群规模
- 显示在线状态
  - 键值存储用户在线状态
  - 使用心跳机制监听更新用户在线状态
